One Guard Pro · Phase 1 · Brief §10.4

Capture flow — design spec

Drafted Aug 29, 2026 against the wh-flush demo job (42 Highland Ave, Somerville — A+ Comfort Club water-heater tune-up, Marcus Reyes). Screens are static mockups; behavior lives here. Design only — nothing here is built.

Principles (from the brief — held to)

Photo first, prose last. The flow opens the camera, not a keyboard. Templates by work type — the A+ Comfort Club tune-up ships first. Structured before unstructured — steppers and chips, not sentences. Voice is a first-class input — transcribe, then confirm. Draft is the default state — every change autosaves locally. Offline-first with an honest queue — never silently drop a capture. Target: under 90 seconds, one hand, gloves on, one bar of signal.

The flow, step by step

0 · Start (from the job brief’s pinned “Start capture”)

The template is pre-selected from the job’s work type — one tap through for the common case, changeable when dispatch got it wrong. The owner’s instruction is restated here because it is the tech’s brief for the visit; it also seeds a template question in step 3. Templates at launch: A+ tune-up (per equipment type), diagnostic, replacement/install, emergency. Emergency is the same flow with every field optional except one photo.

1 · Evidence — the camera is the landing screen

Every shot auto-tags to the job’s equipment record (system + serial, shown in the viewfinder so the tech can trust it). The template suggests a shot list — suggestions, never a gate; chips flip to green as shots are matched. Photo-roll import for shots taken earlier; simple annotation (arrow, circle) on any thumbnail. Low-light is the norm: torch toggle lives in the viewfinder.

2 · Work done — tapping, not typing

Template task rows, multi-select, plus an “Other work…” free-text escape. Materials are chips with an add affordance. Selected tasks are structured events — queryable later (“when was the T&P valve last checked?”), which prose never is.

3 · Findings — measurements shaped to the equipment

Each equipment type carries a measurement schema (water heater: anode %, sediment, temperature rise; boiler: combustion readings, pressures; softener: hardness — extendable per trade). Steppers for numbers, chips for enums; everything skippable. Prior readings render under each field (“Sep 2025: 40% — Comfort Air Mechanical”) — the cross-contractor record earning its keep mid-capture. The owner’s question becomes a chip row (“Start-up noise: Resolved / Persists / Not observed”) so answering the customer is one tap. Voice: hold-to-talk, on-device transcription, Keep / Edit / Discard — transcript is never included without confirmation.

4 · Confidence — kept exactly as-is

Confirmed / Provisional, whole-update, with the existing copy. Per-finding confidence is deferred (open question below) — one more decision per screen is the enemy of the 90-second target.

5 · Next step — chips first, owner-voice text optional

Suggestions derive from template + findings (anode ≥60% → “move replacement planning forward”). Chips make recommendations reportable; the free-text field carries a gentle ~150-char counter, never a hard limit. Multiple chips compose into the owner sentence.

6 · Owner preview — the quality mechanism

Rendered exactly as the Passport will show it: warm voice, jargon translated (“the part that protects the tank from rust”), photos inline, confidence tag visible. Structured inputs compose the prose draft; the tech can edit any line inline before submitting. This is where soft validation fires: “No photo attached — owner records with photos are opened 3× more often. Add one?” with Add photo / Skip. Never a blocking modal.

7 · Submit — closure and momentum

Online: IN REVIEW state, capture-time readout (the metric made visible to the person it measures), a summary receipt, and the next stop one tap away. Offline: the queue screen — per-item status, size-aware Wi-Fi deferral for photo-heavy items with a “Send now” override, and an explicit promise that nothing is dropped.

Draft, interruption, and offline

Every input autosaves to local storage on change; the DRAFT SAVED chip in the header is the visible contract. App kill, phone call, dead battery: reopening the job resumes at the last step. Back never loses input. Close (×) confirms and keeps the draft — a technician’s work is never discarded silently. A returned update re-enters this same flow with the manager’s return reason pinned at the top.

Ergonomics and system extensions

Field controls ≥48px with ≥8px separation (44px minimum for header chrome); primary action pinned to the bottom safe area; type floor 16px body / 14px meta / 13px labels, with 11px reserved for small uppercase tags and kickers only. Two additions to the Modernist tokens, per brief §11.4: 4px radius on touch controls (buttons, inputs, steppers) and the existing pill radius on chips and tags — cards, panels, and rules stay square. Status tags reuse the Phase-0 semantic pairs (QUEUED = progress, IN REVIEW = review, SENT = published). Raw #ec3013 appears nowhere; text-bearing accent surfaces are #ae1800.

New components this flow introduces: capture step shell (header + progress + pinned action), measurement stepper, template chip group, voice input control, shot-list chip, evidence thumbnail with annotate affordance, owner-preview panel, sync-queue row, offline banner.

How we’ll know it works

From brief §16: median capture under 90 s · >90% of captures with at least one photo · returned-update rate under 15% · capture completion >80% of visits within 60 days. The brief’s validation step stands: five Comfort Professor ride-alongs and a paper prototype in a real basement before this is built.

Open questions before build

1 · ServiceTitan overlap — if techs already write job notes in the FSM, which fields here can be pre-filled from the work order so nothing is typed twice? (Brief §17.1 — the biggest unresolved constraint.) 2 · Per-finding confidence — whole-update for v1; revisit if returned-update reasons show mixed-certainty submissions. 3 · Voice transcription — on-device vs. server decides the offline story for voice. 4 · Template ownership — who authors and maintains measurement schemas per equipment type (One Guard, or the contractor’s admin)? 5 · Shot-list depth per template — validate against ride-alongs, not intuition.
